# Version 1: End-to-End MVP

## Objective

Prove that one Web3 company can fund a creator campaign, let invited creators
unlock a real-time reward-block earning stream, and privately settle the
accumulated USDC.

V1 is complete only when the workflow operates end to end. A polished marketplace
with many integrations is not required.

## Fixed Scope

- One submission channel: X content for the initial pilot.
- One primary performance metric selected at the policy gate:
  - Official X impressions if X approves the use case.
  - First-party tracked clicks or conversions if X does not approve it.
- One asset: USDC on Solana.
- One private settlement provider: MagicBlock.
- Invited companies and creators.
- One campaign rule model: eligibility threshold + performance units per reward
  block + reward per block + campaign duration + per-creator cap.
- Real-time earning presentation backed by periodic verified metric snapshots.
- Manual review and dispute handling by an operator.
- English-only web application.

## Stage 1: Complete Simulation

Build the full domain flow without external services:

- Company, creator, and operator test identities.
- Mock company treasury and campaign funding.
- Campaign creation and lifecycle.
- Creator enrollment and mock post submission.
- Deterministic metric snapshots.
- Eligibility unlock, reward-block progress, and cumulative micro-earning
  calculation.
- Live earning stream derived from authoritative snapshots.
- Provisional-to-finalized transition.
- Creator-requested withdrawal and campaign-end settlement.
- Reservation, failure, retry, and reconciliation states.
- Creator and company dashboards.

Exit condition: a seven-day campaign can be simulated from submission through
eligibility, streamed micro-earnings, one or more batched payouts, and final
reconciliation without duplicate earning or payment.

## Stage 2: Real Ledger and Payout Engine

- PostgreSQL schema for campaigns, submissions, snapshots, earning events,
  balances, reservations, payout intents, and audit events.
- Integer USDC base-unit accounting.
- Append-only earning events and rebuildable balance projections.
- Atomic creator-balance and campaign-budget reservation.
- Idempotent payout intent creation.
- Payout failure, retry, release, and reconciliation states.

Exit condition: replayed snapshots and concurrent payout requests cannot create
duplicate earnings or payments.

## Stage 3: Pilot Metric Integration

Use official X metrics only after written use-case approval:

- X OAuth for creator identity.
- Extract and validate an X post ID from a submitted URL.
- Verify post author ownership.
- Poll supported metrics at controlled intervals.
- Store immutable snapshots with provider, observed time, sequence, and raw
  response hash.
- Handle deleted posts, stale data, API failure, and corrected metrics.
- Keep the mock adapter available for tests and demos.
- Require operator review for suspicious performance.

If X approval is unavailable:

- Give each creator a unique campaign tracking link.
- Record verified click events through the platform redirect service.
- Accept signed conversion events from the company where applicable.
- Keep X as the content distribution channel without using impressions as the
  payment oracle.

Both paths use the same snapshot, reward-block, ledger, and payout interfaces.

Exit condition: submitted content accrues earnings from authoritative stored
snapshots, not directly from a live provider response. The frontend displays the
last verification time and updates immediately after each new snapshot.

## Stage 4: MagicBlock Devnet Settlement

- Fund a controlled devnet treasury.
- Accumulate micro-earnings until creator withdrawal or campaign completion.
- Build private USDC transfer through a settlement adapter.
- Sign with an isolated server-side signer.
- Submit and persist transaction signature.
- Poll confirmation status.
- Confirm ledger payment only after chain confirmation.
- Safely retry unknown or failed transactions using idempotency keys.

Exit condition: a creator can request withdrawal of an available balance, and
the system can settle any remaining balance when the campaign ends. Both become
reconciled private payments without exposing a treasury secret to the browser.

## Stage 5: Controlled Pilot

- One company.
- Five to ten invited creators.
- One small, capped campaign.
- Manual finalization approval.
- Manual review before every real payout.
- Full audit log and exportable reconciliation report.
- Clear creator disclosure and dispute contact.
- Official X metrics only if written approval exists; otherwise use first-party
  tracked performance.

Exit condition: at least one funded campaign completes with correct metrics,
ledger balances, payouts, and remaining-budget reconciliation.

## Required Company Features

- Wallet connection and signed authentication.
- Organization profile with one owner.
- Campaign creation, funding, activation, pause, and completion.
- Campaign budget, reserved amount, paid amount, and remaining amount.
- Eligibility threshold, performance units per reward block, reward per block,
  campaign window, creator cap, and withdrawal rules.
- Creator and submission review.
- Campaign-end settlement through the shared payout engine.
- Payout and campaign audit history.

## Required Creator Features

- Wallet connection and signed authentication.
- X account connection.
- Campaign discovery for invited campaigns.
- Join and submit post.
- Eligibility progress, live micro-earning stream, and last verified timestamp.
- Provisional, finalized, reserved, paid, and available amounts.
- Withdrawal request.
- Payout status and private payment receipt.

## Required System Features

- Append-only earning events.
- Exact reward-block and micro-unit calculations using integer arithmetic.
- Immutable metric snapshots.
- Idempotent accrual calculation.
- Atomic creator and campaign budget reservation.
- Payout state machine and reconciliation worker.
- Operator review queue.
- Structured logs, error monitoring, and audit events.
- Unit tests for money math and state transitions.
- Integration tests for concurrent payout attempts.

## Explicit Non-Goals

- YouTube, TikTok, GitHub, referral, sales, or download adapters.
- Public self-service marketplace.
- Fully automated fraud detection.
- Custom Anchor or MagicBlock ER program.
- MagicBlock Private Ephemeral Rollups or delegated accounts.
- Creator self-claim from on-chain escrow.
- Multi-token or cross-chain payouts.
- Fiat on/off-ramp, tax filing, or global compliance automation.
- Mobile application.
- AI features.
- Per-view blockchain transactions.
- A bounty model where the company simply chooses winners after submissions.

## Acceptance Criteria

- A company cannot activate an unfunded campaign.
- Total creator entitlement never exceeds the per-creator cap.
- Total reservations and payouts never exceed campaign funding.
- Replayed metric snapshots never create duplicate earnings.
- No earning accrues before the eligibility threshold.
- Only completed post-threshold reward blocks produce entitlement.
- Partial block progress is preserved but does not overpay.
- The live display never becomes the authoritative source for payment.
- A creator can withdraw available accumulated micro-earnings.
- Campaign completion settles or queues the creator's remaining available amount.
- Concurrent payout triggers produce at most one active payout intent.
- Provisional earnings cannot be withdrawn.
- Failed payments release or retain reservations according to an explicit state.
- Paid status is written only after confirmation is observed.
- Every manual operator action stores actor, time, reason, and affected entity.
- The pilot workflow can be demonstrated from funding through reconciliation.

## V1 Success Gate

Move to V2 only after:

- Three real campaigns have completed.
- At least twenty creator payouts have been reconciled.
- No unresolved double-payment or ledger-integrity incident exists.
- At least two companies request another campaign.
- X data cost and reliability are understood from real usage.
- Legal and policy risks have an explicit operating decision.

Completing the interactive prototype does not satisfy this gate. V2 begins only
after the real controlled pilot meets every criterion above.
